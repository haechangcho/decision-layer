# 실행 기록과 근거

Run은 한 번의 분석 기록입니다. 질문, 사용한 Method, 입력, 쿼리와 결과를 함께 확인할 수 있습니다.

## 결과 읽기

관리자 화면의 **실행 기록**에서 분석을 선택합니다.

1. 질문과 결론을 읽습니다.
2. 분석 경로에서 어떤 Method와 지표를 사용했는지 확인합니다.
3. 단계를 선택해 결과의 표와 그래프를 봅니다.
4. **사용한 설정**, **쿼리**, **출처**에서 계산 근거를 확인합니다.

![예제 데이터로 구성한 실행 기록 화면](../../assets/run-review.png)

단계의 분석 목적은 확인하려던 질문입니다. 실제로 뒷받침되는 결론인지는 결과와 검증 내역을 함께 읽어야 합니다.

## 기간과 검증 확인하기

조회 기간을 선택하지 않으면 입력을 기다립니다. 전체 기간을 조회하려면 명시적으로 선택해야 하며 서버 정책이 허용해야 합니다.

입력이나 데이터 조건이 맞지 않으면 분석이 멈추거나 추가 입력을 요청합니다. 계산 결과가 있어도 검증을 통과하지 못할 수 있으므로 경고와 실패 이유를 확인하세요.

<details>
<summary>API의 기간 설정과 실행 제한</summary>

`scope.date_range`는 날짜 범위, `scope.period: {mode: all}`은 전체 기간 요청입니다. 상대 기간은 실행할 때 실제 날짜로 확정되며 Run에 기록됩니다.

입력 대기 중에는 MCP의 `set_run_scope` 또는 REST의 `PUT /runs/{id}/scope`로 같은 Run을 이어갑니다. REST 요청에는 최신 `base_revision`을 전달합니다. 분석을 시작한 뒤 기간을 바꾸려면 새 Run을 만듭니다.

운영자는 `DL_EXECUTION_POLICY`로 제한을 설정합니다. 기본은 전체 기간 불허, 최대 366일, 쿼리 30개, 결과 50,000행, 비동기 대기 120초입니다. 이 제한은 데이터베이스 비용 추정이나 쿼리 취소를 보장하지 않습니다.

</details>

## 같은 분석을 다시 사용하기

완료된 Run에서 **Recipe로 등록**을 선택하면 절차를 저장합니다. 다음 실행에서는 기간과 대상을 다시 선택할 수 있습니다.

검증에 실패한 계산을 절차로 저장해도 그 결과를 승인한 것은 아닙니다. 다음 실행에도 같은 검증을 적용합니다.

## 필요한 데이터가 없을 때

AI는 찾지 못한 정의와 필요한 보완 사항을 Run에 남길 수 있습니다. 데이터 모델 보완 초안은 담당자가 검토하고 Cube에 적용합니다.

모델을 수정한 뒤 같은 질문을 다시 하면 새 데이터 정의로 분석합니다. 이전 Run은 그대로 남습니다.

## 기록 관리하기

본인의 Run은 목록이나 상세 화면에서 삭제할 수 있습니다. 실행 중인 분석은 작업이 끝난 뒤 삭제합니다. 결과와 쿼리 기록은 함께 삭제되며, 이미 등록한 Recipe는 유지됩니다.

반복할 절차를 구성하는 방법은 [Recipe 만들기](recipes.md)를 참고하세요.
