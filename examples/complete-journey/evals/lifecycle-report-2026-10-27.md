# 문서와 Decision Layer의 작성·재사용·수정 비용 비교

2026-10-27 실행. Codex 세션 68회: 업무 질문 60회, 최초 작성·수정 6회, 과거 기록 확인 2회.

**이번 조건에서는 Decision Layer가 문서와 재사용 코드보다 비용을 줄인다는 가설을 지지하지 못했다.**
전체 세션 시간은 문서 조건 64.94분, Decision Layer 83.33분으로
Decision Layer가 28.3% 더 걸렸다. 수치와 최신 중단 기준 준수는 양쪽 모두 30/30이었다.
토큰도 절감되지 않았다. 이 결과는 한 캠페인 분석 절차를 AI가 작성·수정한 관측값이다.
초기 구간에는 공유 소스 변경이라는 통제 문제가 있었으므로 완전히 고정된 환경의 인과 효과로 읽으면 안 된다.
소스를 격리한 뒤의 업무 실행에서도 비용 절감은 나타나지 않았다.

## 무엇을 비교했나

| 조건 | 분석 지식 전달 | 반복 사용과 수정 |
|---|---|---|
| B: 문서 + 코드 재사용 | 분석가 역할의 Codex가 동일 명세로 절차 문서 작성 | 담당자 역할의 Codex가 Cube 데이터를 조회하고 코드를 만들거나 재사용. 이후 분석가가 문서와 코드를 함께 수정 가능 |
| C: Decision Layer | 분석가 역할의 Codex가 등록 Method 두 개와 Recipe 작성 | 담당자 역할의 Codex가 현재 등록된 절차 실행. 분석 코드는 새로 작성하지 않음 |

대조군에 준비된 OLS 구현을 처음부터 주지 않았다. 첫 작성은 문서만 허용했고,
실제 업무 세션이 만든 코드는 다음 질문과 유지보수에서 재사용하도록 했다.
따라서 이 비교는 같은 분석 지식을 실행 가능한 등록 자산으로 관리하는 것의 추가 효용을 측정한다.
분석 지식이 전혀 없는 AI와 비교한 실험은 아니다.

담당자 질문은 “5번 캠페인 성과가 어땠어? 다음 캠페인을 진행할지 판단하는 데 도움이 될 근거를 알려줘.”처럼 짧게 유지했다.
OLS, 통제 변수, 조회 순서, 중단 기준은 질문에 넣지 않았다. 이 내용은 분석가용 명세와 발행 자산에만 있다.
요청 모델은 양쪽 모두 `gpt-6.1-sol`, medium, CLI 0.160.0이며, 새 세션과 조건별 지속 작업공간을 사용했다.
실제 백엔드 모델의 세부 리비전은 확인되지 않았다.
각 쌍의 실행 순서는 고정 난수로 섞었고, 업무 질문마다 현재 데이터를 다시 조회했다.

데이터는 로컬 complete-journey 데모의 Cube 정의와 적격 가구 코호트다.
캠페인 1·2·3·4·5·6·9·12 및 5·12 재질문으로 버전별 10개 질문을 구성했다.
동일한 8개 관련 시나리오를 반복한 것이며 60개의 독립 데이터셋이 아니다.

| 단계 | 조직 분석 절차 | 확인하려던 가치 |
|---|---|---|
| v1 | 사전 매출·구매빈도 보정 OLS 연관성, 그룹별 최소 30가구 | 최초 작성 및 반복 실행 |
| v2 | 최소 표본 기준을 각 그룹 100가구로 변경 | 변경 전파 및 이전 기준 오사용 방지 |
| v3 | 같은 모형에 HC3 강건 95% 정규 신뢰구간 추가 | 계산·검증·설명 수정의 비용 |
| 과거 기록 확인 | 2번 캠페인의 최초와 현재 결론 비교, 재조회·재계산 금지 | 과거 결과와 절차 버전 추적 |

30·100가구는 실험용 조직 정책이며 통계적 충분성을 보장하는 기준이 아니다.
OLS 결과는 보정 연관성이다. 캠페인 순증 효과나 ROI의 정답으로 간주하지 않았다.

## 시간과 토큰

시간은 **Codex 세션 실행 시간의 합**이다. 실제 사람의 근무 시간, 실험 전체 경과 시간, 청구 금액이 아니다.
세션 내부의 오류 수정·테스트·도구 재호출도 포함했다. 성공한 실행만 골라 재실행하지 않았다.
공통 분석 명세 준비, 계측 도구 개발, 수동 평가, 외부 서버 준비와 별도 검증 게이트는 이 표에 포함하지 않았다.
따라서 제품 도입에 드는 모든 사람의 비용을 측정한 결과는 아니다.

| 구간 | B: 문서 + 코드 | C: Decision Layer | C의 증감 |
|---|---:|---:|---:|
| 최초 작성 | 2.15분 | 11.21분 | +422.5% |
| 기준 변경: 최소 30 → 100 | 8.63분 | 4.85분 | -43.8% |
| 기능 변경: HC3 신뢰구간 추가 | 2.69분 | 6.91분 | +157.1% |
| v1 업무 질문 10회 | 18.42분 | 20.36분 | +10.5% |
| v2 업무 질문 10회 | 15.88분 | 20.67분 | +30.2% |
| v3 업무 질문 10회 | 16.24분 | 17.83분 | +9.8% |
| 과거 결과 확인 1회 | 0.94분 | 1.50분 | +58.8% |
| 전체 34회 | 64.94분 | 83.33분 | +28.3% |

기준 변경은 Decision Layer가 더 빨랐지만, 신뢰구간 추가는 더 느렸다.
두 수정의 합계는 B 11.32분, C 11.76분이다.
수정 한 종류에서의 이득을 일반적인 유지보수 우위로 해석할 수 없다.
이번 30회 반복 사용 구간에서는 초기 추가 비용이 회수되지 않았다.

| 전체 토큰 | B | C | C의 증감 |
|---|---:|---:|---:|
| 입력 전체(캐시 포함) | 9,938,778 | 22,516,734 | +126.6% |
| 캐시 입력 | 8,712,320 | 20,603,392 | +136.5% |
| 비캐시 입력 | 1,226,458 | 1,913,342 | +56.0% |
| 출력 | 127,650 | 167,015 | +30.8% |

CLI 보고값이며 입력 전체에는 캐시 입력이 포함돼 있다. 두 값을 더하면 중복 계산이다.
reasoning 토큰도 출력에 포함된 부분이므로 별도로 더하지 않았다. 실제 API 청구서가 없어 원화·달러 비용을 추정하지 않았다.
모든 68개 세션의 사용량이 기록됐고 프로세스 실패는 없었다. 도구 오류에서 회복한 세션은 있었다.
업무 질문 30회의 MCP 호출은 B 153회, C 288회였다. 반복 실행의 평균 시간은 각각 101.1초와 117.7초다.
도구 호출과 응답 문맥을 줄이는 것이 개선 후보이지만, 호출 수만으로 시간 차이의 원인을 분리해 입증한 것은 아니다.

## 결과 품질과 기록

독립 NumPy 계산으로 그룹 수·평균·계수·HC3 구간을 대조했다.
평가 코드는 합성 자료에서 statsmodels와도 일치했다. 기준 미달 시 추정하지 않는 답도 유효한 결과로 평가했다.
각 조건은 18회 추정과 12회 적절한 중단을 수행했고, v3의 추정 가능한 5회에서는 신뢰구간을 확인했다.

| 관측 항목 | B | C |
|---|---:|---:|
| 수치·최신 중단 기준 일치 | 30/30 | 30/30 |
| 적격 가구 범위 설명 | 30/30 | 21/30 |
| 중복 캠페인과 인구통계 결측 모두 언급 | 30/30 | 14/30 |
| 사용 가능한 로컬 근거 링크 제공 | 28/30 | 30/30 |

30/30은 “답변이 완벽하다”는 점수가 아니다. 설명 누락과 근거 링크 문제는 별도로 평가했다.
설명 평가는 조건을 아는 평가자의 수동 판정이며, 근거 JSON에 개별 답변과 판정 이유를 남겼다.

과거 결과 확인은 **양쪽 모두 성공**했다. 2번 캠페인의 최초 보정 계수 +2.5341,
현재 대상 47가구가 최소 100가구 기준에 미달한다는 사실, 각 절차 버전을 찾아냈다.
추정 허용 여부는 바뀌었지만 “재집행을 확정할 근거가 부족하다”는 사업 판단은 유지됐다는 점도 구분했다.
B는 보관 파일을 읽었고, C는 보관 파일과 과거 Run 3개의 조회 API를 사용했다. 새 데이터 조회나 재계산은 없었다.
시간은 B 56.5초, C 89.7초였다. 이 한 사례에서는 추적성의 비교 우위도 확인되지 않았다.

Decision Layer v2의 코호트 출력에는 원래 전후 30일이어야 하는 설명이 **100일**로 바뀐 오류가 있었다.
표본 기준 변경이 설명 문구에 잘못 반영된 것이다. 계산과 쿼리는 30일을 유지했고,
10개 답변 모두 충돌을 경고했다. v3 작성에서 문구가 수정됐다.
v2 합성 테스트 28개가 통과해도 이 설명 오류는 잡히지 않았다.
또한 C는 저장된 인구통계 결측 진단을 최종 답변에서 생략하는 경우가 있었다.

B의 두 v1 답변은 실제 보관 경로와 다른 타임스탬프의 링크를 제시했다.
다른 v3 답변 하나는 계산 링크가 잘못된 상대 경로였지만, 조회·절차의 정상 링크도 제공했다.
C의 로컬 근거 파일은 확인했으나 답변에 함께 표시된 기본 `localhost:3000` UI 링크는
이 실험의 API 전용 서버와 일치하지 않는다. UI를 통한 근거 접근까지 검증됐다고 주장하지 않는다.

## 통제 문제와 민감도 확인

초기 실행 도중 공유 체크아웃의 CLI·Skill·가이드 파일이 다른 작업에서 변경됐다.
초기 지문에서 일반 가이드 Markdown을 빠뜨려 정확한 노출 시점을 완전히 복구할 수 없었다.
계산 엔진·모델·Cube provider는 확인 시점의 초기 해시와 일치했다.
사용자 변경은 되돌리지 않고 별도 런타임을 만들었으며, **v2 업무 실행부터 v3 및 기록 확인까지** 이를 사용했다.
초기 작성·v1·v2 작성 시간은 환경 영향 가능성이 있는 기술 통계로 남긴다.

- 격리된 v2·v3 업무 실행 20회씩: B 32.12분, C 38.50분
  (C +19.9%).
- B의 CSV 어댑터가 `offset: 0`을 거부한 v1 세 쌍을 양쪽 모두 제외한 업무 실행:
  B 44.01분, C 53.02분
  (각 27회, C +20.5%).

어댑터 제약으로 발생한 네 번의 도구 오류는 Decision Layer 부재의 본질적 비용이 아니다.
전체 합계에서는 그대로 포함하고 위 제외 분석을 함께 제시했다.
데이터·카탈로그와 격리 런타임의 최종 지문 확인은 관측 JSON의 `provenance.after.json`에 기록했다.
대상 데이터 9개 테이블과 카탈로그는 초기 지문과 일치했고, 격리 런타임 172개 파일도 일치했다.

사람 분석가·현업 담당자 실험이 아니며, 작성과 각 수정은 조건당 한 번이다.
모델·서버 지연, 이전 기록의 분량, 새 프레임워크 학습 비용의 영향도 있다.
따라서 유의확률이나 일반적인 제품 ROI를 계산하지 않는다.

## 제품에 대한 판단

이 실험에서 확인한 것은 등록된 절차를 반복 실행하고 버전을 남길 수 있다는 기능이다.
**문서와 재사용 코드보다 더 싸고 정확하게 운영한다는 비교 우위는 확인하지 못했다.**
문서 조건도 코드 재사용과 변경 전파에 성공했으므로, “매번 처음부터 분석하지 않아도 된다”만으로는 차별화가 부족하다.

다음 개선은 관측된 실패에 맞춰야 한다. 담당자 실행에서 읽는 도구 응답과 반복 메타데이터를 줄이고,
분석가의 등록·버전 변경 작업을 단순하게 하며, 계산 결과와 설명의 기간·기준 불일치를 검사할 필요가 있다.
등록된 진단이 최종 답변과 유효한 근거 링크로 전달되는지도 검증해야 한다.
권한 통제나 여러 팀의 감사 요구처럼 이번에 측정하지 않은 가치가 있을 수 있지만, 이번 결과로 입증됐다고 말할 수는 없다.

보존된 사용량·최종 답변·호출 횟수·해시로 확인할 수 있는 범위에서 분석했다.

추가 비캐시 입력의 **91.9%가 반복 실행**에서 발생했다. 최초 작성만 개선해서는 운영 토큰 차이가 해결되지 않는다.
반대로 추가 출력 토큰의 **72.2%는 최초 작성과 수정**에서 발생했다.
반복 실행의 입력 문맥과 작성 단계의 코드·계약 생성 부담을 구분해 줄여야 한다.
수정 단계의 비캐시 입력은 오히려 C가 적었다. 캐시 포함 입력 총량만 보고 모든 단계가 같은 이유로 비싸다고 해석하면 안 된다.

### 반복 실행: 분석보다 주변 절차가 많은지 검증해야 한다

업무 질문당 MCP 호출은 B 5.1회, C 9.6회였다. C는 30쌍 중 6쌍에서만 더 빨랐다.
최종 답변 글자 수 합계는 B 40,958자, C 26,750자로 C가 더 짧았다.
그런데 세션 출력은 C가 더 많으므로, 최종 답변의 길이만 줄이는 것은 적절한 첫 개선이 아니다.
글자 수를 토큰 수로 환산하거나, 이 차이만으로 중간 작업별 비용을 확정하지는 않았다.

MCP `server.py`와 `presentation.py`의 현재 해시는 초기 실험 해시와 일치한다.
코드에서 확인한 개선 후보는 다음과 같다. 이는 실제 비용 비중을 측정한 결과와 구분한다.

- `_compact_run`은 이미 provenance를 요약하지만, Python 단계의 `bindings`, `params`,
  `requested_step`, `input_resolutions`, 결과와 Recipe 안내를 함께 반환한다.
  `start_run`, `get_run`, `complete_run`이 같은 표현을 사용하므로 완료 응답에서도 많은 내용이 다시 전달될 수 있다.
  일상 응답에는 실행 ID·버전·판단에 필요한 결과·필수 진단·검증·근거 참조를 우선 제공하고,
  원본 계약과 상세 기록은 필요할 때 조회하는 방식을 검증할 가치가 있다.
  저장된 원본이나 검증 자체를 삭제하는 개선이 아니다.
- `list_recipes`는 Recipe별 live validation과, 사용 가능한 Recipe의 reuse 조회를 수행한다.
  `_call`은 호출마다 HTTP 클라이언트를 만든다. 하나의 MCP 호출도 여러 REST 요청일 수 있다.
  고정된 Recipe를 반복 실행할 때 목록·상세·후보 탐색을 중복 수행하는지 먼저 계측해야 한다.
  연결 재사용과 메타데이터 revision에 따른 검증 재사용은 후보이며, 실제 데이터·권한·실행 검증은 유지해야 한다.
- 이미 선택되고 바인딩된 Recipe의 업무 실행에서는 현재 버전 확인, 입력 설정, 실행, 결론 저장을 짧은 경로로 제공할 수 있다.
  새로운 질문이나 불명확한 의미에서는 기존 탐색과 확인을 유지한다.
  전체 semantic catalog를 축약하거나 새 검색 계층을 만드는 방안은 이번 로그로 필요성이 입증되지 않았고,
  현재 ADR-124의 정책을 바꾸는 결정이므로 우선 개선안으로 삼지 않는다.

### 실험이 추가한 증거 보관 작업도 분리해야 한다

업무 프롬프트는 양쪽에 계산·조회 근거와 절차 버전을 **작업공간에** 보관하도록 요구했다.
B는 원래 파일에서 계산한다. C는 서버 Run에 이미 기록된 근거를 작업공간으로 다시 내보내는 추가 작업을 하게 될 수 있다.
관측된 C 답변은 로컬 증거와 절차 복사본을 실제로 남겼다.
실행기 역시 매 작업 후 별도로 소스 스냅샷을 보존하므로 보관이 중복되는 구조다.
실행기의 작업 후 복사 자체는 Codex 세션 계측 밖에 있다. 여기서 비용 후보로 지목하는 것은 세션 안에서 에이전트가 수행한 추가 보관 작업이다.

따라서 현재 시간에는 제품의 필수 실행 비용뿐 아니라 실험이 요구한 별도 내보내기 비용도 포함될 수 있다.
얼마를 차지하는지 원시 로그 없이 수치로 빼지는 않는다. 기존 합계도 그대로 유지한다.
다음 실험에서는 B의 파일 기록과 C의 서버 Run 기록이 같은 보존·조회 요건을 만족하면 동등한 증거로 인정하고,
사용자가 별도 내보내기를 요청한 경우에만 그 비용을 추가 측정해야 한다.
이 변경은 수치·현재 정책·과거 버전·필수 진단을 실제로 확인하는 평가를 완화하는 것이 아니다.

### 작성과 수정: 같은 분석을 등록하는 부수 작업을 줄인다

C는 최초 작성에서 계산뿐 아니라 DataInput, 등록, 두 Method, Recipe와 버전, 테스트를 함께 만들었다.
최초 작성 출력은 B 3,924토큰, C 20,000토큰이었다.
C의 첫 발행이 Recipe 1.0.2 / Method 1.0.1이라는 사실은 보존된 최종 답변으로 확인되지만,
중간 수정별 원인과 소요 시간은 현재 자료로 다시 분해할 수 없다.

신뢰구간 추가 때도 C는 6.91분·출력 20,478토큰, B는 2.69분·6,547토큰이었다.
반면 표본 기준 변경은 C가 더 빨랐다. 두 번의 수정만으로 유지보수의 일반적인 우열을 결론내리면 안 된다.

일반 Python 계산과 별도 DataInput이라는 현재 구조를 유지하면서,
검증된 등록 예제·발행 시 버전 참조 갱신·변경 영향 검사로 사람이 직접 맞춰야 하는 작업을 줄이는 것이 후보이다.
계산의 옵션 변경과 의미가 달라지는 변경을 구분하고, 필요한 새 버전과 검증은 그대로 남겨야 한다.
이 작업이 출력과 시간을 줄이는지는 같은 변경을 다시 수행해 측정해야 한다.

### 정확도를 유지하는 개선이 필요하다

C는 더 짧은 최종 답변을 만들면서도 적격 범위와 결측 진단을 생략했다.
따라서 응답 축약은 중요한 진단을 없애는 방식이면 안 된다.
Method 결과에서 반드시 설명해야 할 경고·모집단 범위·중단 이유를 명시하고,
저장된 진단이 최종 답변과 연결됐는지 확인하는 개선을 함께 평가해야 한다.
30일을 100일로 바꾼 설명 오류는 provider 의미와 조직 표본 정책을 분리해 검사해야 한다는 구체적인 회귀 사례다.

### 어느 정도 개선해야 문서 조건보다 나아지나

반복 실행만 비교하면 C의 평균 **117.7초를 101.1초 미만**으로 줄여야 한다(약 14.1% 절감).
하지만 최초 작성·수정·기록 확인 비용을 현재 수준으로 둔 채 **30회 전체 비용**에서 이기려면,
C의 반복 실행 평균이 **81.0초 미만**이어야 한다(현재보다 약 31.2% 절감).

계산은 `C 고정비 1,467.802초 + 30 × C 실행 평균 < B 전체 3,896.607초`이다.
이는 관측 고정비와 B 성능이 유지된다는 가정의 산술 목표이며, 개선 효과 예측이나 통계적 보장은 아니다.
초기 작성도 줄이면 필요한 실행 절감 폭은 작아진다.

우선 검증 순서는 다음이 적절하다.

1. 도구 시작·끝 시각, 모델 호출별 사용량, 응답 크기, 단계별 조회 수와 증거 내보내기 여부를 내구성 있는 경로에 계측한다.
   도구별 응답 바이트를 실제 모델 토큰이나 청구액으로 혼동하지 않는다.
2. 같은 등록 자산으로 기존 응답과 간결한 응답을 비교한다. 정확도·필수 진단·근거 조회가 유지되는지 함께 본다.
3. 중복 탐색과 작업공간 증거 내보내기를 각각 분리해 비교한다. 효과를 확인하기 전에 여러 변경을 묶어 원인을 잃지 않는다.
4. 작성·발행 보조 기능은 별도로 평가하고, 최종적으로 최초 작성부터 30회 사용까지 전체 비용을 다시 비교한다.

이번 분석은 비용 후보를 좁혔다. 각 개선이 실제로 문서와 코드 재사용을 이기는지는 아직 측정하지 않았다.
