# Decision Layer 가치 검증: 세 조건 비교

## 가설과 비교

담당자는 분석 방법을 모른 채 업무 질문만 한다. 분석가가 작성한 지식을
Decision Layer로 실행하면 같은 지식을 문서로 전달했을 때보다 타당한 답을
안정적으로 얻고, 검토·수정 비용을 줄일 수 있는지가 핵심 가설이다.

| 조건 | 데이터/도구 | 분석 지식 |
| --- | --- | --- |
| A / cube | Cube 카탈로그·조회·CSV, 일반 Python | 없음 |
| B / cube_playbook | A와 같음 | campaign-playbook.md만 제공 |
| C / decision_layer | Decision Layer MCP, 같은 Cube | Recipe 2.0.0 + 등록된 두 Method |

A와 B에는 사전 구현된 OLS/캠페인 분석 도구가 없다. 일반 라이브러리로 직접
코드를 작성하는 것은 허용한다. C는 등록된 자산만 실행한다. B의 문서는 C의
순서·변수·검사·기본 기간·해석 한계를 옮긴 것으로, 정답 숫자를 포함하지 않는다.
담당자 질문은 세 조건에서 동일하며 분석 절차를 설명하지 않는다.

주 비교는 **C−B**이며 문서 기반 전달 대비 실행 체계의 효과를 평가한다.
**C−A**는 지식과 제품을 함께 도입하는 효과, **B−A**는 문서화된 지식의 효과다.
이는 실행 코드 준비 여부, 도구와 맥락 제공 방식도 함께 달라지는 비교이며
Recipe라는 객체 하나의 순수한 효과를 뜻하지 않는다.

## 이번 진단 실행: 6회

이전 시험에 쓴 7·8번 캠페인은 제외한다. 10·11번을 결과 조회 전에 선택했다.
질문은 three-arm-cases.json에 고정한다. 기존 Recipe 2.0.0과 두 Method는 수정하지
않는다. 이번 시험 결과를 보고 고친 자산은 새로운 평가 세트로 검증한다.

각 질문 × 세 조건 × 한 번 = 6회. 실행 순서는 seed 20261027로 섞고, 모든 실행은
새 임시 작업공간·세션, Codex CLI 0.160.0, gpt-6.1-sol, medium effort, 600초 제한을
사용한다. 모델 문자열을 고정해도 공급자의 내부 모델 스냅샷은 고정되지 않는다.
모든 실행에서 동일한 승인 검토 모드를 쓴다. 실패·시간 초과·추가질문을 보존하며
성공할 때까지 재시도하지 않는다. 서비스 준비 실패만 별도 인프라 실패로 표시한다.

시작 전 prompt/harness/Recipe/Method/관련 제품 소스 SHA-256, CLI 버전,
Cube 카탈로그, 노출된 Cube 모델이 사용하는 원천 테이블과 분석 뷰의 행 내용
해시를 저장하고 종료 후 재검사한다. Cube 모델이 사용하지 않는 3,679만 행의
프로모션 배치 테이블 causal_data는 제외한다.
이는 변경 탐지이며 여러 Cube 쿼리를 단일 DB 트랜잭션으로 고정하는 기능은 아니다.
등록된 Recipe는 별도 디렉터리에 2.0.0만 노출하고 독립 Run DB를 쓴다.

정답용 SQL과 결과는 에이전트 작업공간에 제공하지 않는다. 출처 테이블로
모집단·평균·중복·결측을 계산하고, 등록 모형 계수는 독립적인 선형대수 계산으로
확인한다. A의 다른 모형은 그 모형과 실행 코드를 별도로 확인하며 계수가 다르다는
이유로 감점하지 않는다. 이번 평가는 구현자가 조건을 아는 상태에서 하는 진단
검토다. 독립 평가자에 의한 맹검 평가를 완료한 것으로 표현하지 않는다.

## 결과를 보기 전에 고정한 채점

주 지표 **타당한 의사결정 지원 응답률**: 아래 V1–V5가 모두 통과해야 1점.
실행 실패 또는 데이터가 충분한데 불필요한 추가질문으로 멈추면 0점이다.
필수 증거가 부족한 사례에서는 올바른 보류/추가질문이 통과 답일 수 있다.
검증하지 못한 항목은 unknown으로 남기고 통과로 계산하지 않는다.

* V1: 올바른 캠페인, 관측 단위, 대상 모집단과 전후 기간을 사용한다.
* V2: 답의 주요 숫자와 비교가 실제 조회/계산에 근거한다. 근거 없는 숫자나
  대상/비대상 혼동이 없다. 대안 모형은 별도로 검증한다.
* V3: 기존 구매 성향·대상 선정과 다른 캠페인의 영향을 고려한다. 차이를
  무조건 효과로 읽지 않는다. 사용한 조정변수와 중요한 미반영 요인을 밝힌다.
  인구통계 변수를 조정에 썼다면 큰 결측과 처리 방법도 밝혀야 한다.
* V4: 실제 계산한 불확실성을 보고하거나 계산하지 못했음을 밝힌다.
  데이터로 입증하지 않은 인과·유의성·ROI·확대 결론을 주장하지 않는다.
* V5: 질문에 대한 판단 한계와 다음에 필요한 근거를 설명한다. 분석/조회
  실패를 성공으로 포장하지 않고 담당자에게 해석 가능한 답을 준다.

별도 보조 지표:

* 조직 절차 준수: 코호트 점검, 중복·결측 점검, 정해진 모형, 입력 검사,
  한계 보고의 5항목. 대안 분석의 타당성 점수와 혼합하지 않는다.
* 증거 재구성: 원천/필터/기간, 실제 계산 코드 또는 버전, 입력 검사 결과,
  결과 숫자의 근거를 제3자가 복원할 수 있는지 4항목. Run 링크 자체에 점수를
  주지 않는다. 대조군 코드·쿼리 로그도 동등하게 인정한다.
* 같은 질문/표현 변경의 결론 일치율: 이번 1회 실행으로는 측정하지 않는다.
* 비용: input/cached input/output, 실행시간, 실제 청구액, 분석가 작성·수정시간.
  캐시 토큰은 입력의 부분집합이며 중복 합산하지 않는다. 추론 토큰도 출력과
  중복 합산하지 않는다. 청구액·작성시간이 없으면 미측정으로 표시한다.

## 본 실험과 통계 분석

6회 결과는 효과크기나 유의성을 확정하는 근거가 아니다. 이후 전문가가 자산과
문서의 동등성을 검토하고, 업무 담당자가 만든 질문을 평가용으로 분리한다.
데모의 나머지 캠페인과 미존재 캠페인·대상 미지정·지원 범위 밖 기간 등 사례를
모두 사전 선정한다. 성공할 사례만 고르지 않는다. 정상 사례와 올바른 보류가
필요한 사례의 응답률은 별도로 보고한다.

본 평가에서는 각 기본 사례를 두 표현 × 두 실행 × 세 조건으로 실행한다.
표현 변경/재실행을 독립 사례로 세지 않는다. 조건 순서는 사례 안에서 균형을
맞춘다. 모델·노출 자산·데이터·실행 예산을 고정하고 정답지는 외부에 보관한다.
두 평가자가 조건명을 가린 답과 표준화한 실행 증거를 채점하고 의견 차이를
조정한다. 제품 고유 도구명 때문에 완전한 눈가림은 어려움을 보고한다.

각 사례 안에서 표현/반복 점수를 평균내고, C−B의 응답률 차이를 주 효과로
보고한다. 사례 단위 paired bootstrap 95% 구간으로 반복 간 의존을 반영한다.
C−A, B−A와 비용·절차·증거 지표는 보조 분석으로 명시한다. 같은 데이터셋과
분석 종류에 국한된 결과를 다른 조직/분석으로 일반화하지 않는다.

30–50개의 질문만으로 개선이 증명된다고 미리 약속하지 않는다. 예를 들어
C−B +15%p를 검출하려 하고 두 조건의 불일치율이 30%라고 가정하면, 단일
paired binary 평가의 정규근사로 약 97개 독립 사례가 필요하다(양측 5%, 검정력
80%; (1.96+0.84)^2×(0.30−0.15^2)/0.15^2). 이는 가정에 따른 계획치이며,
반복 평균·복수 업무·실제 불일치율에 맞춰 시뮬레이션으로 다시 산정한다.
데모의 제한된 캠페인 수로는 탐색적 검증부터 하고 다른 업무/데이터를 추가한다.

제품 가치 판단 기준도 결과 전에 정한다: 주 지표 개선, 또는 품질을 유지하면서
검토·수정의 총비용 감소. 비열등성 허용폭은 전문가가 정하고 별도 표본수를
계산한다. 품질이 나빠졌는데 속도만 빨라진 결과를 성공으로 바꾸지 않는다.
관측 개선이 없으면 그대로 보고하며 승리하는 지표를 사후 선택하지 않는다.

## 비용 분석

반복 실행 총비용은 초기 작성비 + N×(실행비 + 검토비) + 유지보수비다.
C와 B의 건당 비용차가 양수일 때만 추가 작성비 / 건당 절감액으로 손익분기
실행 횟수를 계산한다. 작성시간을 기록하지 않은 기존 자산으로 이 수치를
만들어내지 않는다. 토큰 단가를 확인하지 않은 CLI 사용량을 달러로 환산하지 않는다.

Codex 명시 모델과 JSON 실행은 [공식 CLI 문서](https://learn.chatgpt.com/docs/developer-commands#codex-exec)를
확인하고 설치된 CLI 도움말로 옵션을 검증했다. 이것이 API의 가격이나 모델
스냅샷 고정을 보장하지는 않는다.
